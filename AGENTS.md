3. Before coding inspect fresh main, relevant PR heads/touched files, live path claims and the local-source recovery record. Acquire one AF lane with exact paths; do not auto-select old U/R/C/F prompts.

6. Menus, text, voice and channels use one server-authorized operation and receipt. Models propose; users authorize consequential spending. Unverified phone numbers are not identity proof.
7. No provider execution without validated input, authorization, idempotency, timeout, recovery and reconciliation. Screenshots/paid claims do not independently release P2P escrow.
8. Implement connected source and meaningful tests. Use typed errors, account-fenced cache, denied/offline/retry states, accessible controls and low-data defaults. Native changes need a new qualified signed binary; obey docs/FLUTTER-RELEASE-AND-SHOREBIRD-POLICY.md.
9. Main is the default development integration target. Merge scoped, compatible changes promptly after reviewing the diff and running checks relevant to the change. Routine development CI/CD triggered by a main merge is authorized by the owner; do not hold source in an integration branch merely because main builds or deploys. Use another target only for a concrete source conflict or explicit owner direction.
10. Keep real tests, compiler checks and branch protections. Fix failures introduced by the change; document pre-existing unrelated failures and unavailable runners without requiring full-app/device/provider/release qualification for every PR. Documentation-only changes require diff/link review, not app builds. Do not disable tests or use admin bypass to hide a regression. Destructive data migrations, paid resources and financial/provider activation still need applicable authorization; development deployment does not prove release readiness.
11. Keep secrets and personal data out of Git/logs. No destructive production migrations, paid resources or external messages without applicable authorization.
12. Handoffs include base/head SHAs, PR, paths, acceptance IDs, commands/results, blocked checks, remaining source, safe merge target and next action. Record PLANNED / PARTIAL_IMPLEMENTATION / IMPLEMENTED_UNVERIFIED / VERIFIED_E2E / DEPLOYED_VERIFIED honestly. Structural document checks prove only document consistency.

# C06 — Internal crypto transfer integration contract

Status: PARTIAL_IMPLEMENTATION / UNVERIFIED. Superseded by canonical requirements where they differ.

Requirements: W06/W07/W08, C06, J09/J11. The transfer is an **internal custody-backed ledger movement** between authenticated Masanawa human user IDs within the same tenant, **not** an external blockchain payout, Credits payment, fiat remittance or chat message. No financial action is automatic on selecting a DM recipient. The policy/market/provider gate always precedes an available quote.

## HTTP contract (authenticated)
- `GET /v1/financial/crypto/internal/capabilities`: `{enabled:boolean,reason:string|null,routes:[{providerCode,asset,network}]}`. Never advertise enabled without a configured KYC/AML/limits decision authority and qualified live custody route evidence. Unknown provider/eligibility means disabled.
- `POST /v1/financial/crypto/internal/quotes`: `{quoteRequestId,recipientUserId,providerCode,amount}`. Requires authenticated sender, canonical recipient account, qualified custody-backed route, explicit approval from injected risk policy and policy-specified zero fee. Returns `{quoteId,senderUserId,recipientUserId,asset,network,amount,fee,policyRevision,createdAt,expiresAt,quoteRequestId}`. Replaying the same quoteRequestId with different terms fails. Quotes expire after 120 seconds; historical replay never renews the quote.
- `POST /v1/financial/crypto/internal/transfers`: `{requestId,quoteId,confirmed:true}`. A server-authenticated source identity, matching unexpired unconsumed quote, **fresh** custody qualification and risk policy revision, and sufficient exact asset+network balance are mandatory. The server atomically stores immutable transfer and opposing debit/credit entries under the same custody-balance advisory lock as withdrawals/conversions. No provider payout API is called. Returns `{transferId,quoteId,requestId,senderUserId,recipientUserId,asset,network,amount,fee:"0",completedAt,status:"completed",kind:"internal-book-transfer"}`. Request replays yield the same committed receipt, even after quote expiry; conflicting replays fail.
- `GET /v1/financial/crypto/internal/requests/:requestId`: authenticated sender-only read for uncertain-response recovery.
- `GET /v1/financial/crypto/internal/transfers/:transferId`: authenticated sender or recipient receipt read.
- `GET /v1/financial/crypto/internal/history?limit=50`: authenticated participant history, `{transfers:[...]}`, max limit 100.

All routes use the existing platform financial session authorization, not an AI tool token. Errors are typed; unknown SQL/provider details are never returned to customers. The Wallet screen's `InternalCryptoTransferScreen` uses the same API transport and authenticated session as existing wallet. It holds a pending requestId/quoteId in encrypted, account-keyed storage prior to HTTP send, and refuses a second transfer while outcome is uncertain. Receipt readback is authoritative. It must never erase an unresolved journal on a timeout or turn a chat send into payment.

## Mandatory qualification before enabling production

The injected `TransferRiskPolicy` must be implemented by an audited, real identity/KYC/AML/rate/region/amount-limit decision source. It must reject disabled/revoked/deleting/restricted senders or recipients and disallowed assets/networks/markets, return a stable policy revision and **explicit zero-fee decision**; nonzero fee policies fail closed until a platform fee ledger leg is designed and approved. No policy adapter is provided by this draft and Gateway composition does not inject one by default, so **sending is disabled**. A boolean `confirmed` is not equivalent to a strong transaction-authorization factor; integrate quote-bound reauthentication/step-up according to the approved identity/risk policy prior to enabling.

Handle/phone/contact resolution is not yet integrated; the prototype boundary accepts canonical verified human user IDs only. Shared C01 contact identity, C02 human DM, C07 assistant action and R17/C08 navigation owners must reuse the **same** quote and transfer IDs and avoid parallel ledger implementations. Transaction initiation from Chats and Assistant is **NOT IMPLEMENTED**. Transaction history pagination and account-deletion journal cleanup still require integration. Rollout needs a real qualified NOWPayments account, disposable database migration/recovery proof, server and device tests, approved safeguards, monitoring and rollback.

## Database invariants

Migration `packages/commerce/migrations/0110_crypto_internal_transfers.sql` creates immutable quote/transfer/entry tables and a deferred commit-time balanced double entry assertion. `commerce.crypto_all_ledger_entries` unifies provider and internal book entries; `accountBalance`, tenant liability, and platform liability in `crypto-repository.ts` must **all** use it (not only Wallet reads). A unique sender request and consumed quote prevent duplicates. Canonical `identity.tenants` and both `identity.users` must be active at quote and execution, protected by `FOR SHARE` transaction row locks; the quote also checks current spendability, and transfer repeats the balance check under the custody lock. Money uses PostgreSQL `numeric(38,18)`; no floating arithmetic in settlement.

Financial schema changes are forward-only. Never backfill/enable this migration against production without a verified off-account backup and disposable restored rehearsal. Never weaken the existing custody/withdrawal reserve semantics in order to let internal transfers proceed.

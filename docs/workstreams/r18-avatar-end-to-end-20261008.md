## Implemented source-to-device avatar flow

- **API/storage:** `POST/DELETE /profiles/me/avatar` authenticate the same canonical customer session as the public profile. Binary `image/png` upload is capped at 2 MiB, strict PNG decoding/checksums/scanline/bounds/decompression are verified, ancillary metadata is discarded, and S3 PUT/DELETE use SigV4. Immutable random per-upload URLs are bound to owner/tenant hash prefixes, not client-provided arbitrary URLs. The server validates an encoded optimistic avatar version so stale phones cannot delete/overwrite another device's photo.
- **Durability:** additive `packages/talks/migrations/0015_profile_avatar_objects.sql` journals staged/active/orphaned/deleting object lifecycle. Staging happens *before* S3 PUT; owner-scoped profile URL CAS and activation are in one PostgreSQL statement; replaced/removed objects enter recoverable garbage queue. Claim batches use `FOR UPDATE SKIP LOCKED`, stale leases are reclaimed, and cleanup errors are retried. Background sweeper runs every ten minutes when storage is configured and closes during both shutdown paths. Older APK `PATCH /profiles/me` photo removals also retire their managed image atomically.
- **Mobile:** already-present image_picker opens camera or gallery, a drag/zoom crop sheet redraws decoded pixels to a fresh 512×512 PNG (so source metadata is not transmitted), typed Dio streams upload with authenticated bearer client and a current-image precondition. The merged editor shows Add/Change Photo and saves deferred Remove Photo through the canonical media DELETE path; it refuses to discard unsaved name/bio edits. A successful server-reloaded avatar invalidates public profile caches. Settings now displays the saved public name/avatar, with account-session fallback; the home header already displays the public avatar from merged #425.
- **Authored tests:** PNG corruption/metadata/decompression/dimensions, S3 signing/bucket key validation/404 deletion/failed PUT, SQL CAS/journal/garbage lease, owner authorization, stale-device conflicts, route content type and version, client HTTP transport and Flutter pixel crop, existing profile name/bio and legacy removal safety. ## Handle rename safety audit / hold

The schema and runtime audit found that `talks.safety_enforcement` and `talks.safety_reports` use exact profile handle strings; `talk_safety/repository.ts` resolves profile user IDs by exact `public_profiles.handle` and reads/writes enforcement by exact `target_id`. Pending `talks.human_invitations.invitee_handle` and `talks.persona_profiles.owner_handle` also embed handles. **A simple UPDATE public_profiles.handle would bypass moderation rules and break old links.** Work on a future alias reservation/migration must atomically preserve old-handle resolution, reserve retired handles, preserve immutable safety-report evidence, rekey or canonically resolve enforcement and invitation/Twin lookups, and reject collisions/races. Safe rename is NOT implemented and must not be enabled by mobile UI alone. Public display name/avatar does synchronize across header and Settings, while authenticated account/legal-name storage remains separate by design.
